# Инструкции для агентов проекта

## Цель и источники требований

Разрабатываем мини-маркетплейс объявлений на FastAPI и Vite с React. Для MVP 1.0 автор создаёт объявление с фотографиями, отправляет его на проверку, получает причину отказа, исправляет объявление и подаёт повторно. Публичный каталог показывает объявление только после одобрения модератором.

Критерии конкретной задачи и зависимости читаем в [GitHub Issues](https://github.com/akhtyamovpavel/KisGithubFlow2026/issues). Команды и настройки сверяем с `README.md`, зависимости с lock-файлами, доступные операции с кодом и OpenAPI. Требования ниже описывают целевое поведение MVP. Наличие требования в документе не означает, что соответствующая возможность уже реализована.

В окружении Павла перед работой читаем разделы «Как писать текст для людей», «Как писать КОД» и «Как писать ФОРМУЛЫ» в `~/CLAUDE.md`. Начальные инструкции о SPARC и claude-flow к Codex не относятся.

## Команда и GitHub Flow

- Работаем в отдельных сессиях Codex: daniil, yulia и timofey. Имена участников не считаем GitHub-логинами. Задачи между вкладками передаёт пользователь. Без явной просьбы не создаём субагентов и не отправляем сообщения от имени пользователя.
- Перед началом читаем issue, проверяем зависимости и состояние рабочей копии через `git status`. Сохраняем существующие изменения пользователя и других участников.
- Выполняем `git fetch origin --prune` и создаём ветку от свежего `origin/main`. Для feature используем `feat/<номер-issue>-<english-name>`, для исправлений `fix/<номер-issue>-<english-name>`, для документации `docs/<english-name>`. В `main` напрямую не коммитим.
- Ограничиваем PR одной задачей. В описании указываем результат, команды выполненных проверок и ограничения. Для выполненной задачи пишем `Closes #<номер>`. Для частичной работы пишем `Refs #<номер>` и оставляем issue открытой.
- Получаем ревью другого участника. После устранения замечаний и успешных применимых проверок CI слияние выполняет teamlead по поручению пользователя. Собственный PR самостоятельно не одобряем.
- После слияния удаляем рабочую ветку, если её изменения больше не нужны. Не переписываем историю `main` и опубликованных тегов.
- При пересечении работы над API, моделями или `frontend/src/App.jsx` согласуем интерфейс и порядок слияния через пользователя. Операции с общей базой и миграциями выполняем последовательно.

## Установка и запуск

Используем Python 3.12 или новее, uv и Node.js 22. Команды backend выполняем из корня репозитория:

```bash
uv sync --project backend --frozen
```

При первом запуске копируем `backend/.env.example` в `backend/.env`, если файла настроек ещё нет. Генерируем секрет командой `openssl rand -hex 32` и сохраняем значение в `MARKETPLACE_AUTH_SECRET_KEY`. Не выводим секреты в отчёты и логи. Применяем миграции и загружаем категории:

```bash
uv run --project backend --frozen alembic -c backend/alembic.ini upgrade head
uv run --project backend --frozen --directory backend python -m app.seed_categories
uv run --project backend --frozen uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000 --reload
```

Документация API доступна по адресу `http://127.0.0.1:8000/docs`. Для первого модератора заполняем `MARKETPLACE_MODERATOR_EMAIL`, `MARKETPLACE_MODERATOR_DISPLAY_NAME` и `MARKETPLACE_MODERATOR_PASSWORD` в локальном окружении, затем выполняем:

```bash
uv run --project backend --frozen --directory backend python -m app.create_moderator
```

Команды frontend выполняем из каталога `frontend`:

```bash
npm ci
npm run dev
```

По умолчанию Vite использует порт 5173. Переменная `VITE_API_URL` задаёт адрес API. При смене порта frontend обновляем `MARKETPLACE_CORS_ORIGINS` полным адресом с портом. Занятый порт не освобождаем остановкой другого проекта без просьбы пользователя.

## Объявления, доступ и модерация

- Публично возвращаем только объявления в статусе `published`. Ограничение действует для каталога, поиска, страницы объявления и фотографий. Email, история и причины отказа не входят в публичный ответ.
- Проверяем права на backend при каждом запросе. Автор управляет своими черновиками и фотографиями. Автор и модератор получают доступ к закрытым данным объявления согласно контракту API. Публичная регистрация создаёт только роль `user`.
- Сохранение черновика не запускает модерацию. Черновик может не удовлетворять правилам подачи и не иметь фотографий. Объявления в `pending` и `published` не редактируем через операции черновиков.
- Перед первой и повторной подачей применяем общие серверные правила: заголовок от 5 до 120 символов, описание от 20 до 5000 символов, неотрицательная цена с точностью до двух знаков, активная категория и от 1 до 5 фотографий. Возвращаем нарушения по полям. Невалидное объявление не попадает в очередь.
- Для каждой успешной подачи создаём новую версию со снимком полей и фотографий, затем переводим объявление в `pending`. Повторный запрос не создаёт вторую активную подачу. Снимки и решения прошлых версий сохраняем при исправлениях.
- Модератор принимает решение только по текущей версии в `pending` и не проверяет собственное объявление. Одобрение требует подтверждения всех правил и переводит объявление в `published`. Отказ требует непустой причины и переводит объявление в `rejected`. Повторное или устаревшее решение возвращает HTTP 409.
- При повторной подаче снова проверяем исправленные поля и фотографии. Сохраняем предыдущую причину отказа, решение и автора решения в истории.
- Проверяем фотографии по содержимому. Поддерживаем JPEG, PNG и WebP размером до 5 МБ на файл. Генерируем имена хранения на сервере. При замене и удалении сохраняем файлы, на которые ссылаются снимки истории.

## Изменения кода и базы данных

- Используем существующие зависимости, API-клиент и сервисы. Для изменения зависимостей обновляем соответствующий lock-файл. Не добавляем библиотеки без необходимости задачи.
- Для изменения схемы создаём новую миграцию Alembic. Сначала сверяем текущую вершину миграций с актуальным `origin/main`; применённые миграции не переписываем. Не сбрасываем локальную базу ради устранения конфликта схемы без согласования.
- Согласуем изменение формата ответов между backend и frontend. На интерфейсе различаем загрузку, пустую выдачу, ошибку и успешный результат. Ошибки правил показываем у соответствующих полей.
- Не коммитим `.env`, токены, пароли, SQLite-файлы, загрузки пользователей, виртуальные окружения и каталоги сборки. Используем примеры настроек без секретов.
- Пишем циклы и условия многострочно, избегаем неявной склейки строковых литералов. Имена кода и файлов кода пишем по-английски, русские документы называем по-русски. `AGENTS.md` и `README.md` сохраняют стандартные имена. Скрипты создаём в проекте, а не во временных каталогах.

## Проверки и готовность задачи

Не запускаем и не добавляем тесты без просьбы пользователя. При запросе проверки используем команды из корня репозитория:

```bash
uv run --project backend --frozen ruff check backend
uv run --project backend --frozen pytest backend/tests
```

Сборку frontend выполняем из каталога `frontend`:

```bash
npm run build
```

Перед выдачей текстовых документов в окружении Павла запускаем `python3 /home/akhtyamovpavel/Teaching/CU/PromProg/2026/scripts-docs/lint_text.py <файл>`. В отчёте перечисляем только реально выполненные проверки. Если проверку не запускали или команда завершилась ошибкой, сообщаем причину. Документационные PR могут не запускать CI из-за фильтров путей; отсутствие запуска не называем успешным CI.

Считаем задачу готовой после выполнения критериев issue, обновления необходимых команд и описаний API, ревью и слияния PR. Для выпуска MVP 1.0 проверяем полный сценарий: автор создаёт объявление с фото, модератор отказывает с причиной, автор исправляет и подаёт повторно, модератор одобряет, объявление появляется в каталоге. До одобрения проверяем отсутствие объявления и его фотографий в публичном доступе. Частичная подготовка CI не закрывает задачу полной приёмки.

Тег и GitHub Release публикуем по явному поручению пользователя на согласованный коммит. Для промежуточной версии используем prerelease и перечисляем готовые возможности и ограничения.
